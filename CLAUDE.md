# MegaOrbitals: notes for Claude

A Paper **26.1.2** plugin (Java 25, Maven) with 1322 orbital strike cannons.
The owner is not a programmer, so explain results in plain language.

## Build

- JDK 25 is at `C:\Program Files\Eclipse Adoptium\jdk-25.0.3.9-hotspot`. Maven defaults to JDK 21, so set `JAVA_HOME` first:
  `export JAVA_HOME="/c/Program Files/Eclipse Adoptium/jdk-25.0.3.9-hotspot"; mvn -o clean package`
  (drop `-o` if a dependency is missing).
- The build runs `ConfigExporter`, which writes `src/main/resources/configs/<id>.yml` for every cannon and rewrites `CANNONS.md`.
  Commit those generated files along with the code.
- Check a build with: number of `dev/megaorbitals/cannons/*.class` in the jar = number of `configs/*.yml` = the expected cannon count.
  The exporter prints `FAILED <class>` if a cannon can't be created without a server.

## How cannons work

- One class per cannon in `src/main/java/dev/megaorbitals/cannons/`, extending `Cannon`. They are found automatically.
  The id is the class name in lower case.
- Constructor: `super(name, iconMaterial, lore...)`, then `warning(ticks, "#hex")`, `noBlockDamage()` and `option(key, default, comment)`.
  Override `strike(Strike s)` (and optionally `warn`).
- Use the helpers instead of raw Bukkit calls:
  - `Strike`: `at`, `later`, `every`, `loop`, `victims`, `players`, `damage`, `explode`, `blocks`, `tag`, `mob`, `hunt`, `tempAttribute`, `allies`, `surface`, `randomPoint`, `give`, `tell`.
  - `Fx`: particles, `display`, `itemDisplay`, `title`, `dustLine`, `dustRing`, `dustSphere`.
  - `Blocks`: `set` and `put`, and the `box`, `columns`, `sphere` and `throttle` jobs.
- Cannons are registered as event listeners, so they can have `@EventHandler` methods.
  Keep per-strike state in instance maps; each cannon class has a single instance.
- Every cannon needs a tier and a category: add its id to the lists in `Catalog.java`.

## Rules that are easy to break

- **Never change blocks with raw `setType` / `setBlockData` in a cannon.** Use `Blocks.set` or `Blocks.put`, so `/orbital undo` can put them back.
  Undo only records changes made while a strike is running. Code in `s.later`, `s.every`, `s.loop` and `s.blocks` is covered.
  Wrap block changes made from an event handler in `s.run(() -> ...)`.
- Respect `s.breaks()` (the `break-blocks` setting). Cannons that must build something tell the shooter and stop if it is off.
- **No static fields that touch Bukkit registries** (`PotionEffectType`, `Enchantment`, `Attribute` arrays...).
  The build-time exporter creates every cannon without a server, so these must only be used inside methods.
- `s.every(period, times, ...)` repeats forever when `times <= 0`. Clamp counts that come from config.

## The arsenal (1000 generated cannons)

- `Arsenal.java` holds 40 `Payload`s and 25 `Pattern`s. `Combo.java` is their shared base class.
- Each combination is a tiny generated class in `cannons/` marked `// Generated by tools/generate_arsenal.py`.
  Don't edit those classes by hand. Change `Arsenal.java` and run `python tools/generate_arsenal.py`.
  The script refuses names that clash with a hand-written cannon.
- Arsenal tiers and categories are set through `Catalog.define`, not the lists in `Catalog.java`.
- Omega skips arsenal cannons unless `include-arsenal` is true.

## Addon API (1.6.0+)

- `dev.megaorbitals.api`: `MegaOrbitalsAPI` (register/unregister/look up/fire/give), `OrbitalFireEvent`, `OrbitalStrikeEvent`.
  `MegaOrbitals.registerCannon` / `unregisterCannons` do the work. `OrbitalListener.onPluginDisable` removes an addon's cannons.
- Treat the public methods of `Cannon`, `Strike`, `Fx`, `Blocks`, `Catalog` and the `api` package as a public API.
  Don't rename or remove them. If you must change them, bump `MegaOrbitalsAPI.API_VERSION` and note it in the changelog.
- `examples/example-addon` must keep compiling. CI builds it against the current version (`mvn install` first, then
  `mvn -f examples/example-addon/pom.xml package -Dmegaorbitals.version=<version>`).
- Docs for owners and addon developers are in `docs/`. Update them when commands, config keys or the API change.

## Releasing

- Bump the version in `pom.xml`, `src/main/resources/plugin.yml` (`version:` and the cannon count in `description:`),
  the `config.yml` header and `megaorbitals.version` in `examples/example-addon/pom.xml`.
  Update the count in `README.md` and `docs/`, and give the version's `CHANGELOG.md` section its date.
- Only commit or push when the owner asks. Then push `main`, and after that push the tag `vX.Y.Z`.
  The tag must match the `pom.xml` version.
- GitHub Actions (`.github/workflows/build.yml`) builds the tag and publishes the release.
  It uses that version's `CHANGELOG.md` section as the release text.
- Run `git fetch` before pushing: the owner sometimes commits on GitHub directly.
  Check that the `main` push succeeded before pushing the tag.
